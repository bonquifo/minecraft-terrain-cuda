The GPU is 857× faster than single-threaded vanilla, 49× faster than vanilla using every core of a 16-core desktop CPU, and 87× faster than our own C++ port on 32 threads. That C++ port is the debugging reference (an interpreter of the density graph, written for clarity and verified first), not a tuned CPU implementation: on one thread it runs at 0.56× vanilla's JIT-compiled speed. CV is the coefficient of variation over all timed repetitions (warm-up repetitions excluded).

Correctness

Bit-exactness is the definition of done: every block state, every biome and every density value is compared for equality with vanilla, with no tolerance. Device code is compiled with -fmad=false -prec-div=true -prec-sqrt=true -ftz=false, never fast-math; every optimization below preserves the exact IEEE operations or replaces them by integer work with a written proof that the result is identical.

The reference oracle runs the real game classes (Minecraft 26.3 server jar via Fabric Loom, on this machine only) and dumps values for 32 seeds (8 fixed, 24 random) at 18 chunks each: a 3×3 block at the origin, chunks near and far, chunks at the world border (±1,874,999) and at the 32-bit wrap points of the noise lattice, over the full build height (y = −64 to 319). mccuda_tests --set full (RESULT: PASS (bit-exact)):

The R-tree tie rule is not a corner case. Over 5 seeds (28,372,992 quart lookups each, region 128×128 plus borders), the last-result candidate changed the chosen parameter leaf at 547–703 ppm of lookups and the biome at 329–461 ppm, because quantized climate values regularly land exactly on a box boundary, which puts the target inside two adjacent boxes at distance 0. Returning the plain nearest leaf would put a wrong biome in roughly one quart in 2,600. Both generators reproduce the rule exactly; it acts along each chunk's chain of lookups. The only history dependence vanilla has beyond that is the first lookup of a chunk, which starts from whatever the worker thread looked up last; the oracle and our generators start it empty.

The engine behaviours that exactness depends on (two evaluation semantics, the R-tree tie rule, aquifer prefill, heightmap order in the material rules) are written up in the engineering notes below.

How the speedup was found

What mattered

  • FP64 is the bottleneck on a GeForce part. The RTX 5090 runs FP64 at 1/64 of the FP32 rate. Minecraft 26.3's gradient noise is FP32 inside, but every octave still does about 29 FP64 operations on coordinates (scale, wrap, offset, floor, fraction). A static SASS count of the corner kernel showed ~7,000 FP64-pipe instructions against ~16,000 FP32 ones, which at 1:64 means FP64 dominates by an order of magnitude.
  • v1 replaces Mth.floor's three FP64 compares by one cvt.rmi.s32.f64 (which saturates like Java's cast; NaN is tested on the bit pattern) and decides GradientNoise.wrap's range test with integer compares on the IEEE bit pattern.
  • v2: every corner-level noise is an unshifted volume noise at a fixed scale, so each axis's coordinate setup depends on that axis alone. Its exact result is tabulated once per distinct coordinate (y: once per seed for the 49 corner rows; x/z: per corner column) and reused, which removes all FP64 from the corner kernel without changing a single operation.
  • v3/v6: the biome zoom (BiomeManager) looked up for nearly every stone block, because 26.3 checks a cave biome in the material rules, was most of the surface kernel (79% in an ablation build). Its squared offsets take only 8 × 1,024 distinct values (table), and an FP32 pre-filter with a proven error bound (|f − d| < 1.14e-6 for distances ≤ 6.31) leaves the FP64 comparison to genuine near-ties only: in 2,147,483,648 random lookups 50,492 took that path, with 0 mismatches.
  • v4/v5: neighbouring chunks need the same positions. A GPU radix-sort dedupe evaluates each distinct position once, for any chunk list: for the 64×64 region, 2,117,632 surface-level lookups are 144,778 distinct ones (14.6×), and 102,400 corner columns are 66,049 (1.55×).
  • v7: the generated material-rule tree was noinline, which kept the whole rule context in local memory; inlining it cut the stage by 38%.
  • v8: an R-tree DFS seeded with the distance of the neighbouring quart's leaf (+1) provably returns the same first-minimal leaf while pruning most of the tree; the last-result tie rule is resolved with parallel tie flags and a warp per biome chunk.
  • v9: two pipeline slots. The first attempt overlapped nothing: copies run in submission order, so a download enqueued before the next batch's upload blocked it. Enqueueing each download after the following upload fixed it (Nsight Systems timeline).

Method

  • Machine: AMD Ryzen 9 9950X (16 cores / 32 threads), 128 GB RAM, NVIDIA GeForce RTX 5090 (170 SMs, 32 GB, driver 591.86, WDDM), Windows 11. CUDA 13.1, MSVC 14.44, JDK 25.0.4.1. GPU state sampled right after the GPU runs: 2910 MHz SM (max 3090 MHz), 44 °C, 265.28 W, P1.
  • Clocks unlocked (locking needs administrator rights); variance is reported instead: CV over repetitions and, for the headline configurations, the spread of independent process runs.
  • Workload: seed 123456789, square regions anchored at chunk (0, 0). Vanilla and the CPU port use 16×16 (1 to 4 threads) or 32×32 chunks; the GPU uses 128×128 (it needs the larger region to fill the device). Warm-up repetitions run first (JIT, allocations) and are not timed.
  • Fairness: vanilla computes biomes once per chunk of the region plus border, exactly what its BIOMES step does; the GPU recomputes the biomes of tile borders shared between batches, which is extra work on its side. Vanilla's worker threads share one RandomState like a server; its R-tree last-result cache is left alone (live-server behaviour) in throughput runs and reset per chunk in the dump runs.
  • Profiling: Nsight Systems for kernel times and timelines, cuobjdump for register/stack use and SASS instruction mixes, CUDA events per stage, and targeted ablation builds. Nsight Compute could not collect counters: it reports ERR_NVGPUCTRPERM (counter access is admin-only on this machine and was not changed).

Scope and limits

  • Included: biomes (multi-noise climate, exact R-tree search including its last-result tie rule), final density with all cave noises, NoiseBasedAquifer, doFill, the material rules with ore veins, clay bands, eroded-badlands and frozen-ocean extensions, and the heightmap updates they depend on.
  • Not included: carvers (they were not requested), structures (Beardifier is empty without structure starts), blending with old-world chunks, features, lighting. In a live server the first biome lookup of a chunk starts from the worker thread's previous lookup; ours starts empty, like the oracle, so a server can differ where that first lookup is an exact tie (see Correctness).
  • Decisions taken without the author: Minecraft 26.3 on native Windows; game-derived data (IR, terrain model, oracle dumps) is extracted locally into the git-ignored data/ and never committed; clocks unlocked; overworld only; the optional Fabric/JNI mod was not started.

Engineering notes

Notes on the behaviours of Minecraft 26.3's terrain generation that had to be reproduced exactly, and on how the GPU code stays exact while being fast. Everything here was found by reading public signatures/bytecode of the locally prepared game jar and by comparing against the oracle; no game source is reproduced in this repository.

1. Two evaluation semantics

26.3's density functions are float-valued and have two evaluation paths, and they do not produce identical bits:

  • Volume path (sampleVolume): used to generate a chunk's density, the climate for biomes, ore-vein density and richness, and the aquifer surface-level prefill.
  • Point path (sampleValue): used for aquifer barrier/floodedness/spread/lava queries, the ore-vein filler gap, and the find_top_surface probes.

Differences that matter:

volume point
noise coordinates block * (scale * frequency) (block * scale) * frequency
gradient dot product (gx*x + gz*z) + gy*y (xz part reused over y) (gx*x + gy*y) + gz*z
interpolation z, then x, then incremental steps in y lerp3 at the point
min / max keep the first argument unless the second is strictly smaller/larger Math.min/max, with range-based short cuts
mul / div plain zero short-circuit on the first operand

The code generator (cuda/codegen/gen_router.py) emits a separate evaluator per context, and each context has fixed semantics. Mixing them up produces values that differ in the last bit for a small fraction of positions, enough to flip blocks.

2. The compiled graph

Vanilla rewrites the density graph before sampling: references are inlined, structurally equal cache nodes are merged, and functions that do not depend on an axis are evaluated on slices. The IR exporter (oracle/.../IrExporter.java) mirrors these rewrites, and the binary operations carry vanilla's compile-time decisions: constant detection, division by a constant as a multiply by the float reciprocal, and min/max pruning from value ranges. Those decisions change results, so they are made once, at export time, exactly as vanilla makes them.

3. Random numbers

  • Xoroshiro128++ with positional factories: fromHashOf seeds from MD5 of the name, at(x, y, z) from Mth.getSeed. The legacy 48-bit LCG is still used for biome temperature noise.
  • nextDouble is (bits >>> 11) * 2^-53 computed in double. A decompiler rendering suggested float arithmetic, and the bytecode (l2d, dmul) settled it. Lesson: verify literals and casts against bytecode.
  • Noise construction sums amplitudes with a compensated stream sum, so plain summation is wrong.

4. Biomes

  • The six climate parameters are sampled at quart resolution (every 4 blocks) with the volume path and quantized as (long)(value * 10000f).
  • Lookup is an R-tree over 7,594 parameter boxes (19 children per node, built with stable sorts). Search descends into a child only if its box is strictly closer than the best leaf so far, and accepts a leaf only if strictly closer.
  • The tree keeps a last-result candidate per thread and starts each search from it. On an exact distance tie this makes the result depend on the previous lookup. The rule is: the candidate wins if it reaches the minimal distance, otherwise the first minimal leaf in DFS order. A live server's result therefore depends on which chunk a worker thread generated before. The oracle resets the candidate per chunk, and so do the CPU port and the GPU.
  • BiomeManager picks a quart per block from the 8 surrounding quarts with a seeded "fiddle". The obfuscated seed is SHA-256 of the world seed, read little-endian.

GPU: L (the first minimal leaf) is computed in parallel with a DFS whose initial bound is the distance of a neighbouring quart's leaf plus one; that provably yields the same L. The tie rule then needs the previous result only where the previous L* also reaches the minimum. Those flags are computed in parallel, and one warp per chunk resolves the rare windows that contain one.

5. Aquifers

  • 16x12x16 grid. Cell locations are random per grid cell, and fluid status is derived from the surface level around the cell, the floodedness and spread noises, and a lava-noise check for fluid levels at or below -10.
  • The surface level comes from find_top_surface. Positions inside the aquifer's constructor prefill window (quarts 4c-4 .. 4c+6) use volume semantics. Other positions are sampled lazily with point semantics. Both orders must match.
  • Blocks above a per-chunk skip height use the global fluid picker directly.

6. Material rules

  • A column is walked top-down. Stone depth above and below, water height and surface depth feed the rule tree: about 150 conditions, 110 block results, 43 noise thresholds, 2 vertical gradients, 2 ore veins (new in 26.3's material rules) and clay bands.
  • The heightmap is updated on every block placement. The slope condition reads neighbour heights, and vanilla processes columns in x-major, z-minor order, so a neighbour's height is either before or after both extensions. The GPU reproduces this with three height snapshots: initial, after the eroded-badlands extension, and after the frozen-ocean extension, which is dry-run in a first pass.
  • 26.3 checks a cave biome for almost every stone block below the preliminary surface, so the zoom (section 4) runs for most blocks of a chunk.

7. Floating point

  • Java has no FMA contraction and is strict IEEE. Device code: -fmad=false -prec-div=true -prec-sqrt=true -ftz=false. Host code: /fp:precise, with contraction verified by a unit test.
  • Mth.floor is (int) Math.floor(v), and Java's cast saturates with NaN going to 0. On the device that is a single cvt.rmi.s32.f64 plus a NaN test on the bit pattern.

8. GPU exactness techniques

technique why it is exact
per-axis noise coordinate tables (AxisRec) the same IEEE operations, computed once per distinct coordinate and reused
zoom square table same expression, tabulated over its 8 x 1,024 possible inputs
zoom FP32 pre-filter error bound proof: corners more than 8e-6 above the FP32 minimum cannot be (or tie) the minimum; survivors use the exact FP64 comparison
distance compares on bit patterns non-negative doubles order like their bit patterns
position dedupe each value is a pure function of position
bounded R-tree search any bound above the minimum yields the same first minimal leaf

9. Oracle data

oracle/regen.ps1 writes, under the git-ignored data/:

  • gamedata/26.3/overworld_ir.json: the optimized density graph (floats as raw bits, doubles as hex), with value ranges and axis dependence per node.
  • gamedata/26.3/overworld_terrain.json: the material-rule tree, block palette, biome parameter list and biome climate.
  • oracle/26.3/{quick,full}/: per seed, named-function volumes (L1), final density (L2), core block fill (L3), and biomes, aquifer fill and final terrain. The layout is ((y - minY) * 16 + z) * 16 + x, with SHA-256 manifests.
