Inside the GPU run

The density core alone

The first milestone ported only the density and the block fill, without aquifers or material rules. Vanilla here is NoiseChunk + sampleVolume(finalDensity) + the substance decision per block; the GPU row uses the first, naive kernels, kept as the baseline implementation cuda-v0. On one thread vanilla spends 2.18 ms per chunk on this core against 8.46 ms for the whole TERRAIN step, so the core is only 26% of the work. Biomes, aquifers and the material rules are the larger part, which is why the full step was the target.

Correctness

Bit-exactness is the definition of done: every block state, every biome and every density value is compared for equality with vanilla, with no tolerance. Java is strict IEEE with no fused multiply-add, so device code is compiled with -fmad=false -prec-div=true -prec-sqrt=true -ftz=false, never fast-math. Every optimization keeps the exact IEEE operations or replaces them by integer work with a written proof that the result is identical.

The evidence comes in three layers, from single values to a running game.

Inside the running game

The in-game recording (Videos) uses a Fabric mod in a development client. Inside a 136×136-chunk region it puts the GPU's output in at vanilla's own seams: the noise fill writes the GPU's finished blocks, the surface pass is skipped because its result is already there, and biomes are swapped in the same way at doCreateBiomes. The client reads a dump the GPU wrote beforehand (1.8 GB); it does not call CUDA itself.

For control takes the same mod leaves generation to the game and compares each chunk with the GPU's dump as the server generates it: the biomes right after doCreateBiomes, and every block right after buildSurface, the end of the TERRAIN step.

With structures on, every mismatch is in a chunk whose density a structure reshapes (the Beardifier, for villages, trail ruins and the like): 524 of the 1,142 such chunks differ, 826,034 blocks in all, and the other 9,521 chunks match exactly. That adaptation is outside this project's scope, so the recordings use worlds without structures. One more thing the dump does not carry: vanilla's doFill also marks aquifer fluid blocks that should start flowing once the chunk is finished. In GPU-filled chunks those fluids stay still until a neighbouring block changes; the blocks themselves are identical.

The recorded frames still differ, and are expected to. The GPU take differs from the first vanilla take in 5.1% of pixels per frame on average (by more than 8 of 255), and the two vanilla takes differ from each other by about as much, 5.6%. The differences are trees. A chunk's trees are placed while its neighbours may already be decorated, so where trees compete for space the outcome depends on the order in which the server's worker threads finish chunks.

What exactness takes

These are the behaviours of 26.3's terrain generation that are easy to get almost right. They were found by reading public signatures and bytecode of the locally prepared game jar and by comparing against the oracle; no game source is reproduced. The longer write-up is docs/ENGINE_NOTES.md.

Two evaluation semantics

26.3's density functions are float-valued and have two evaluation paths that do not produce identical bits. The volume path (sampleVolume) generates a chunk's density, the climate for biomes, ore-vein density and richness, and the aquifer's surface-level prefill. The point path (sampleValue) answers the aquifer's barrier, floodedness, spread and lava queries, the ore-vein filler gap and the find_top_surface probes.

The code generator (cuda/codegen/gen_router.py) emits a separate evaluator per context, each with fixed semantics. Mixing them up changes the last bit at a small fraction of positions, which is enough to flip blocks. The gradient dot product shows how small the difference is:

The compiled density graph

Vanilla rewrites the density graph before sampling: references are inlined, structurally equal cache nodes are merged, and functions that do not depend on an axis are evaluated on slices. The IR exporter (oracle/.../IrExporter.java) mirrors these rewrites, and the binary operations carry vanilla's compile-time decisions: constant detection, division by a constant as a multiply by the float reciprocal, and min/max pruning from value ranges. Those decisions change results, so they are made once, at export time, exactly as vanilla makes them.

Random numbers

Xoroshiro128++ with positional factories: fromHashOf seeds from the MD5 of a name, at(x, y, z) from Mth.getSeed. The legacy 48-bit LCG still drives the biome temperature noise. nextDouble is (bits >>> 11) * 2^-53 computed in double: a decompiler rendering suggested float arithmetic, and the bytecode (l2d, dmul) settled it. Noise construction sums the octave amplitudes with a compensated sum, so plain summation is wrong.

Biomes and the R-tree tie rule

The six climate parameters are sampled at every quart (4 blocks) with the volume path and quantized as (long)(value * 10000f). The lookup is an R-tree over 7,594 parameter boxes (19 children per node, built with stable sorts): the search descends into a child only if its box is strictly closer than the best leaf so far, and accepts a leaf only if it is strictly closer. BiomeManager then picks a quart per block from the 8 surrounding quarts with a seeded offset; that seed is the SHA-256 of the world seed, read little-endian.

The tree keeps a last-result candidate and starts each search from it. On an exact distance tie the candidate wins if it reaches the minimal distance; otherwise the first minimal leaf in DFS order wins. This is not a corner case: over 5 seeds (28,372,992 quart lookups each, region 128×128 plus borders) the candidate changed the chosen leaf at 547–703 ppm of lookups and the biome at 329–461 ppm, because quantized climate values regularly land exactly on a box boundary. Returning the plain nearest leaf would put a wrong biome in roughly one quart in 2,600. Both generators reproduce the rule along each chunk's chain of lookups. Vanilla's only other history dependence is the first lookup of a chunk, which starts from whatever the worker thread looked up last; the oracle and our generators start it empty, so a live server can differ where that first lookup is an exact tie. Inside the running game none of the 17,075,712 biome values compared above differed.

The GPU finds the first minimal leaf of every quart in parallel (with a bounded search, v8 below). The rule then needs the previous result only where the previous leaf also reaches the minimum:

Aquifers

A 16×12×16 grid. Cell locations are random per grid cell; fluid status comes from the surface level around the cell, the floodedness and spread noises, and a lava-noise check for fluid levels at or below −10. The surface level comes from find_top_surface: positions inside the aquifer constructor's prefill window (quarts 4c−4 to 4c+6) use volume semantics, other positions are sampled lazily with point semantics, and the GPU must use the same split. Blocks above a per-chunk skip height use the global fluid picker directly.

Material rules

A column is walked top-down. Stone depth above and below, water height and surface depth feed the rule tree: about 150 conditions, 110 block results, 43 noise thresholds, 2 vertical gradients, 2 ore veins (new in 26.3's material rules) and clay bands. 26.3 checks a cave biome for almost every stone block below the preliminary surface, so the biome zoom runs for most blocks of a chunk.

The heightmap is updated on every block placement, and the slope condition reads neighbour heights. Vanilla processes columns in x-major, z-minor order, so a neighbour's height is from before or after both surface extensions. The GPU walks all columns in parallel and reconstructs what each column would have seen from three height snapshots, with the frozen-ocean extension dry-run in a first pass:

How it got fast

Starting from a straight port of the reference code (v0), each step was chosen from profiling data, measured right after the change on the same 64×64 region (4,096 chunks), and re-verified on the full oracle set before it was committed. What mattered, with the code

FP64 is the bottleneck on a GeForce part

The RTX 5090 runs FP64 at 1/64 of its FP32 rate. Minecraft 26.3's gradient noise is FP32 inside, but each octave sets up its three coordinates in FP64, about 29 FP64 operations per octave. A static SASS count of the v0 corner kernel showed about 7,000 FP64 arithmetic, compare and conversion instructions against about 16,000 FP32 ones, so at 1:64 the FP64 work dominates by an order of magnitude.

v1: floor and wrap as integer work

Mth.floor is (int) Math.floor(v), and Java's cast saturates with NaN going to 0. On the device it becomes one conversion instruction with the NaN case decided on the bit pattern, and the wrap range test becomes integer compares on the IEEE bits:

v2: per-axis coordinate tables

Every corner-level noise is unshifted and at a fixed scale, so each axis's coordinate setup depends on that axis alone. Its exact result is computed once per distinct coordinate and read back:

v3 and v6: the biome zoom

The material rules check a cave biome for nearly every stone block, and the BiomeManager zoom was 79% of the surface kernel in an ablation build. Its squared offsets take only 8 × 1,024 distinct values (v3), and an FP32 pre-filter with a proven error bound leaves the FP64 comparison to near ties (v6):

v4 and v5: deduplication across chunks

Neighbouring chunks need the same positions. For the 64×64 region, 2,117,632 surface-level lookups are 144,778 distinct ones (14.6×), and 102,400 corner columns are 66,049 (1.55×). The dedupe runs on the device for any chunk list:

Tried and reverted

  • Per-column memo of the 2D rule noises: no measurable change.
  • Per-column cache of zoom corner hashes, and a per-chunk hash table: both slower (local-memory traffic and scattered loads beat recomputing).

Method and scope

Method

  • Machine: AMD Ryzen 9 9950X (16 cores / 32 threads), 128 GB RAM, NVIDIA GeForce RTX 5090 (170 SMs, 32 GB, driver 591.86, WDDM), Windows 11. CUDA 13.1, MSVC 14.44, JDK 25.0.4.1. GPU state sampled right after the GPU runs: 2910 MHz SM (max 3090 MHz), 44 °C, 265.28 W, P1.
  • Clocks unlocked (locking needs administrator rights); variance is reported instead: CV over repetitions and, for the headline configurations, the spread of independent process runs.
  • Workload: seed 123456789, square regions anchored at chunk (0, 0). Vanilla and the CPU port use 16×16 (1 to 4 threads) or 32×32 chunks; the GPU uses 128×128 (it needs the larger region to fill the device). Warm-up repetitions run first (JIT, allocations) and are not timed.
  • Fairness: vanilla computes biomes once per chunk of the region plus border, exactly what its BIOMES step does; the GPU recomputes the biomes of tile borders shared between batches, which is extra work on its side. Vanilla's worker threads share one RandomState like a server; its R-tree last-result cache is left alone (live-server behaviour) in throughput runs and reset per chunk in the dump runs.
  • Profiling: Nsight Systems for kernel times and timelines, cuobjdump for register/stack use and SASS instruction mixes, CUDA events per stage, and targeted ablation builds. Nsight Compute could not collect counters: it reports ERR_NVGPUCTRPERM (counter access is admin-only on this machine and was not changed).

Vanilla is timed through its own code path. The inner loop of the vanilla benchmark makes the calls that buildTerrain makes before carvers, on real ProtoChunks whose biomes were generated in phase 1:

Scope

  • Included: biomes (multi-noise climate, exact R-tree search including its last-result tie rule), final density with all cave noises, NoiseBasedAquifer, doFill, the material rules with ore veins, clay bands, eroded-badlands and frozen-ocean extensions, and the heightmap updates they depend on.
  • Not included: carvers (they were not requested), the terrain adaptation around structures (measured in the game, see Correctness), blending with old-world chunks, features and lighting. A live server's first biome lookup per chunk can differ on an exact tie (see Exactness).
  • Decisions taken without the author: Minecraft 26.3 on native Windows; game-derived data (IR, terrain model, oracle dumps) is extracted locally into the git-ignored data/ and never committed; clocks unlocked; overworld only. A Fabric mod (client/) exists only to record the in-game videos from a precomputed dump; running CUDA inside the game (JNI) was not attempted.
